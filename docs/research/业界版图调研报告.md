## B. 深挖:对设计最有用的 8 个机制

**1. Anthropic 的 lead-worker 委派与 token 经济学。** 多 agent 系统 = lead(Opus 4)派生并行 subagent(Sonnet 4),每个 subagent 有独立上下文窗口,本质是"并行算力扩容+信息压缩器"。内部评测超单 agent 90.2%,但代价明确:agent 用量 ≈ 聊天 4×,multi-agent ≈ 15×;BrowseComp 上 token 用量单项解释 80% 的性能方差。两个可直接搬走的细节:(a) **委派必须带四要素**——目标、输出格式、工具与来源指引、任务边界,否则子代理重复搜索(他们早期"研究芯片短缺"一句话派发,三个子代理做了同一件事);(b) **按复杂度缩放投入的硬规则写进提示词**——事实查询 1 agent 3-10 次调用,对比类 2-4 个 subagent 各 10-15 次,复杂研究才 >10 个。早期失败模式包括"简单查询生成 50 个子代理"。([来源](https://www.anthropic.com/engineering/multi-agent-research-system))

**2. Anthropic 的"产物落盘"与终态评估。** 附录给出的机制与设计高度同源:subagent 把工作存到外部系统(文件系统),只给 lead 传轻量引用,防止多级转发中的"传话游戏"失真与 token 复制开销;上下文将满时 agent 把计划存入 Memory、spawn 干净的新 subagent 接续。评测上,对会改状态的 agent **只评终态**(最终文件/环境是否正确),不逐轮验证过程——这正是"主 agent 只读视察+状态蒸馏"的理论依据。([来源](https://www.anthropic.com/engineering/multi-agent-research-system))

**3. Claude Code 的权限分级样板。** Subagent 定义就是一份权限契约:YAML frontmatter 声明 `tools`/`disallowedTools` 白名单、`model`(可路由到便宜模型)、`permissionMode`;内置 Explore/Plan 是只读代理(Write/Edit 直接拒绝),且跳过 CLAUDE.md 以求快与省。硬上限:嵌套派生默认 ≤3 层(`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`),并发 ≤20。Agent teams 更进一步:teammate 的权限弹窗**冒泡给 lead 批**;auto 模式下分类器把"另一个 agent 转述的批准"视为不可信输入;`TaskCompleted` hook 可用退出码 2 拦下"虚假标记完成"。但边界也很清楚:不能在 spawn 时给 teammate 单独设权限模式、**明确不做嵌套团队、不能罢免 lead**。([subagents](https://code.claude.com/docs/en/sub-agents)、[agent teams](https://code.claude.com/docs/en/agent-teams))

**4. OpenAI 的两种所有权模型。** Agents SDK 把选择讲得最透:handoffs = 专长 agent 接管本轮对话;agents-as-tools = 经理保持最终答复权,把专长当有界能力调用(`Agent.as_tool()`)。两者的组合即"二级整合层"的标准形态。SDK 另带 guardrails、会话持久化与 usage 追踪;`orchestrating via code` 提供 while+evaluator 循环与结构化输出路由。([来源](https://openai.github.io/openai-agents-python/multi_agent/))Codex 侧的 worktree 设计(每 agent 独立工作树)是"主 agent 派发子文件夹"的直接先例;第三方整理稿还记录了一个有意思的观察:子线程独立上下文能"缓解总是写出 100% 通过的测试"——写手看不见测试结果时反而更诚实([CodexGuide](https://raw.githubusercontent.com/freestylefly/CodexGuide/refs/heads/main/docs/advanced/08-thread-management.md))。

**5. Google A2A:契约先行的完整答案。** Agent Card 是公开可发现的登记清单(名称、技能、接口、**security 字段声明认证方案**),`/.well-known/agent-card.json` 标准路径;Task 是有状态工作单元(可查、可取消、可推送通知);企业特性一节要求:生产强制 HTTPS、凭证走 HTTP 头(OAuth2/OIDC)、**按 skill 授 OAuth scope**、最小特权、审计关键事件、OpenTelemetry 追踪。最妙的是"任务中二次凭证":agent 执行到一半需要新系统的权限时,向客户端**请求**额外凭证再继续——这就是"动态申请权限"的协议级先例。A2A 还坚持 agent 互不透明:不共享内部记忆、工具与资源,与"写手只读写自己文件夹"同构。([llms.txt](https://github.com/a2aproject/A2A/blob/main/docs/llms.txt)、[企业特性](https://a2a-protocol.org/latest/topics/enterprise-ready/))

**6. Magentic-One 的引导者循环与自纠错。** Orchestrator 维护两个结构化 ledger:外环 task ledger(已证事实、待查事实、待推导事实、**带限定的猜测**——猜测允许但只能卡住时用),内环 progress ledger 每轮回答五问(完成了吗?在死循环吗?有进展吗?下一个谁说话?给他什么指令?)。卡滞计数 >2 就触发反思、修订计划,**并且强制清空所有 agent 的上下文重来**——用上下文重置换一致性。权限上,Coder 写代码但只有 ComputerTerminal 能执行,读写执行天然分置。评测用 AutoGenBench:每个任务新 Docker 容器,防 agent 间互相污染与危险副作用。([论文](https://arxiv.org/abs/2411.04468))

**7. MetaGPT / ChatDev:组织图与 SOP 的学术原型。** MetaGPT 把 SOP 编码进提示序列:PM 产出 PRD→架构师→项目经理→工程师→QA,**角色间传递的不是聊天记录而是标准化产物**(发布-订阅消息池),用"文档即契约"压住级联幻觉——这与"契约先行+同步通知 MD"同构。ChatDev 是"CEO/经理/手"组织图的最早原型:CEO+CTO 双 agent 定决策, Programmer+Reviewer 循环写码, Tester+Programmer 循环调试;其 "communicative dehallucination" 用讲师-助手两轮问答逼出可验证答案。([MetaGPT](https://arxiv.org/abs/2308.00352)、[ChatDev](https://arxiv.org/abs/2307.07924))

**8. Manus 的成本第一性原理。** 生产 agent 的第一指标是 **KV-cache 命中率**:Manus 输入:输出 ≈ 100:1,缓存命中 token 与未缓存价差 10×($0.30 vs $3.00/MTok)。两条工程纪律:提示前缀保持稳定(系统提示开头放时间戳=烧钱)、上下文只追加不回写。这直接支持成本哲学:**与其每次任务重建完整上下文,不如让"按需生灭"的短命 agent 前缀尽可能共享**。([来源](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus))

## C. 三个关键问题

### C1. 业界如何做"agent 间权限分级与审批"?

**现有最佳实践(四级):**
1. **静态工具白名单**(最普遍):Claude Code subagent 的 `tools`/`disallowedTools`;CrewAI 的 agent 级+task 级双指定;A2A 的按 skill OAuth scope + 最小特权原则。
2. **只读角色内置化**:Claude Code Explore/Plan 禁写禁执行;Magentic-One 的 Coder/Terminal 把"写"与"执行"拆成两个角色——这是 22 条里"写手无执行权、执行权集中测试群"的唯一架构先例。
3. **人工/上级审批冒泡**:Claude Code agent teams 的权限弹窗冒泡到 lead;teammate 在 plan 模式产出计划交 lead 批准;A2A 任务中二次凭证机制(agent 中途申请额外权限)。
4. **反越权协议**:agent 间消息被明确声明"不构成用户授权";auto 模式分类器审查 agent 间消息内容,把转述的批准当不可信输入。

**空白:** 权限几乎是"spawn 时静态配置"或"单点人工弹窗"。没有业界系统实现**多级审批链**(上级代批、越界自动升级)、**运行时边界伸缩**(申请-审批-改文件夹范围)、或**组织级罢免流程**。Claude Code 甚至明说:不能 per-teammate 设权限模式、teammate 继承 lead 的 bypassPermissions 有安全风险、明确不做嵌套团队——即主流刻意把层级压在两层。分级审批链与三级组织是真实的空白。

### C2. 业界如何防"agent 说谎/谎报完成"?

**现有最佳实践(五招,全部围绕"用环境事实替代 agent 自述"):**
1. **终态评估**:Anthropic 对改状态的 agent 只验证最终环境状态(文件/测试/页面),不信过程汇报;编码任务用测试做 ground truth("Code solutions are verifiable through automated tests")。
2. **结构化状态账本**:Magentic-One 的 task/progress ledger 把"事实/猜测"分开记,猜测必须带限定语——制度化地不允许 agent 把猜测当事实汇报。
3. **对抗性交叉审查**:Claude Code agent teams 官方用例——5 个 agent 各持假设"互相试图推翻,像科学辩论";Anthropic 的 voting 并行模式;MetaGPT/ChatDev 的 reviewer/tester 角色循环。
4. **输出消毒与来源核验**:Claude Code 对 subagent 报告扫描"指令形文本"并加"此为 agent 之言,无用户授权"头;LLM-as-judge 的评分维度里专设"引用准确性:引用的来源是否支撑结论"。
5. **审计与追踪**:A2A 要求审计关键事件 + OpenTelemetry 全链路。

**空白(且有官方自认证据):** Claude Code 文档承认"**teammates 有时忘记把任务标为 completed,从而卡住下游依赖任务**"——即业界承认"完成状态"不可信,但解法只是"人工手动改状态或提醒"。没有任何系统把谎报当组织问题治理:没有证据链、没有罢免程序、没有强制的全局诚实约束(全靠系统提示词软约束)。"诚实宪法+证据罢免+人批"填补的是治理层,不是机制层。

### C3. 业界如何控制多 agent 的 token/内存成本?

**现有最佳实践(六招):**
1. **KV-cache 优先**:前缀稳定+只追加(Manus,价差 10×);Claude Code 给 subagent 单独的缓存 TTL(默认 5 分钟,可调 1 小时)。
2. **按复杂度缩放**:Anthropic 的 scaling 规则(简单问题禁开多 agent);Manus"遮蔽工具而非移除工具"减少选择开销。
3. **模型分层路由**:lead 用强模型、worker 用便宜模型(Opus lead + Sonnet workers;Claude Code 内置 web-fetch 用 Haiku;"低档思考"有直接先例)。
4. **上下文隔离即扩容**:每个 subagent 独立窗口,主对话只收摘要;LangGraph 的 `output_mode` 精细裁剪进入主上下文的消息历史。
5. **文件系统做上下文**:Anthropic 附录——大产物落盘、传引用;计划存 Memory 防 200K 截断。
6. **上下文重置换正确性**:Magentic-One 每次改计划清空全员上下文。

**空白:** Anthropic 自己给出两条坏消息:multi-agent ≈ 15× token,"需要所有 agent 共享上下文或 agent 间强依赖的领域(如多数编码任务)今天不适合 multi-agent"。业界没有解决"**短命 agent 反复冷启动重复读同一批文件**"的进程级内存复用问题,也没有"agent 数量与成本的组织级预算线"。"按需激活用完即散+每域 2-3 写手的编制控制"正是冲这两个空白设计的;但要注意反方证据——Anthropic 认为**编码任务的多 agent 收益低于研究任务**(可并行度低、协调开销高),立项论证需正面回应这一点(git 工作树+文件边界恰恰是回应手段,Codex/Claude Code 的 worktree 实践支持)。

## D. 结论:22 条设计 vs 业界先例

### 已有直接先例(照着实现即可,12 条)

| 专家评审团参谋 / 对抗找茬 | Claude Code agent teams 官方"科学辩论"用例;Anthropic voting;AutoGen critic 终止条件 |

| 按需激活用完即散 | Anthropic/Claude Code subagent 生命周期;DSH 同款 |
| git 式发布同步链 / 微型 git 同步 / base_commit 三路合并 | Codex/Claude Code worktree + git 标准操作(机制现成,组织化用法是增量) |

### 部分先例,本设计组合更系统(7 条)
- **动态工作边界(申请-审批-伸缩)**:A2A 有"任务中二次凭证"的协议先例,但无人做到"运行时改文件夹边界"。
- **分级审批链(上级代批/越界升级)**:Claude Code 有"冒泡给 lead 批",仅一层、且不能按 teammate 配置;多级链是空白。
- **三级组织(CEO/经理/手)**:ChatDev/MetaGPT 有组织图(但角色是流水线而非管辖层级);CrewAI 只有一层经理;Claude Code 明确禁嵌套团队。**主流工程系统全部压在两层,三层嵌套管辖是真实创新点。**
- **执行权集中测试群**:Magentic-One 有角色分置先例,但"执行权集中给独立测试群"是组织级升级。
- **专家罢免(证据+人批)**:只有 shutdown 请求(可被拒绝),无证据驱动的罢免程序。
- **横向通信需审批**:Claude Code teammate 可自由互发消息(设计上就是横向自由),审批式横向通信是反主流设计——需要论证收益(省 token/防串供)。
- **每域写手 2-3 个的编制**:Anthropic 的缩放规则给了数量参照,但无"编制"概念。

### 确实稀缺、可作创新点主张(3 条)
1. **文件重要性分级**:所有系统把文件当平等对象(Manus 的 todo.md 是唯一的"优先文件"实践),"按重要性分级读写预算"无先例。
2. **全局诚实宪法(不得隐瞒)+ 罢免治理闭环**:业界防谎报全靠"评估终态+对抗审查",无宪法层与组织治理层(证据链→罢免→人工批准)。
3. **审批式横向通信 + 组织级 token 编制**:业界横向通信全自由、成本全靠开发者自觉,无组织级预算与通信治理。

### 一条必须正面回应的反方证据
Anthropic 明确认为多数编码任务"不适合 multi-agent"(并行度低、协调开销高、15× token)。22 条里有四条(worktree 隔离、契约先行、终态测试群、文件边界)恰好是针对这些痛点的工程解,建议在立项书里以"Codex/Claude Code 已用 worktree 验证了代码域的隔离可行性"作正面回应,并把"价值密度高的任务才开组织"写进 scaling 规则(Anthropic 的教训:简单查询开 50 个子代理是头号失败模式)。
